# Preview and visual lifecycle policy (Policy 1)

**Status.** Accepted project policy (Luiz and Chat), marker
`PREVIEW_VISUAL_LIFECYCLE_POLICY_1_ACCEPTED`. It is a project-method decision, not a scientific
experiment. `CLAUDE.md` states the binding rule for executed scientific steps; this document
defines the two artifact trees it refers to.

## Two artifact trees and the Git record

| tree | role | in Git | lifetime |
|---|---|---|---|
| `./previews/` | **machine-facing experimental memory** | no (gitignored) | the current project stage |
| `./visuals/` | **human-facing scientific memory** | no (gitignored) | the whole project |
| Git | **the durable scientific record** | yes | permanent |

The durable scientific result always belongs in Git:
- code;
- contracts and reports;
- numerical summaries, provenance and hashes;
- the commands that regenerate artifacts;
- acceptance decisions.

The two trees hold artifacts that the Git record describes and can regenerate.

## `./previews/` — machine-facing experimental memory

- **Gitignored.**
- Holds current-stage run evidence and regenerable intermediate data. It may hold large artifacts:
  EXR renders, patches, maps, logs, saved measurements, evaluations and whole run directories.
- **Stays available for the life of the current project stage**, because replay, comparison,
  audit and visual generation may need it.
- **Is disposable after that stage**, once no current work depends on it.
- **Is not the permanent scientific record.**
- Lives in the repository checkout (`/home/lvelho/rd/f3d-vision/previews/`). New current-stage
  previews are **not** placed in external archival directories.

**OLD-PREVIEWS.** `/home/lvelho/temp/previews-2026.09.28` holds the reference trees of earlier
stages. No new experiment writes there, and current `./previews/` does not symlink into it. Its
remaining trees may be deleted only after a separate dependency audit shows that no current gate
or investigation needs them.

## `./visuals/` — human-facing scientific memory

- **Gitignored.**
- **Persistent for the lifetime of the project**, and compact relative to `./previews/`.
- For scientific inspection, qualitative evaluation, intuitive understanding, presentations,
  papers and demonstrations.
- **Generated by Git-tracked tools** whenever possible. Reports record each visual's path and its
  exact regeneration command.

A diagnostic plot alone does **not** necessarily satisfy the visual requirement. Whenever the
phenomenon under study has a meaningful spatial or temporal representation, the visual should
expose that phenomenon itself, not only controller bookkeeping.

## What visuals are for

1. intuitive insight;
2. qualitative scientific evaluation;
3. explanation of causal behavior;
4. demonstrations and presentations;
5. comparison across project stages.

For an active-perception experiment, prefer visuals that answer:
- What was perceived?
- What was attended?
- What changed because of this observation?
- How did the epistemic state change?
- How did persistent 3-D memory change?
- Why did the next action occur?
- What was the final result?

## Canonical active-perception visual

The default conceptual frame:

    +-----------------------------+-----------------------------+
    | 1. SCENE / ATTENTION        | 2. FOVEATED OBSERVATION     |
    | selected target             | left + right observations   |
    | current fixation            | stereo/depth patch if useful|
    +-----------------------------+-----------------------------+
    | 3. CYCLOPEAN / EPISTEMIC    | 4. PERSISTENT 3-D MEMORY    |
    | support / unknown / etc.    | accumulated reconstruction  |
    | current fixation            | new geometry highlighted    |
    +-----------------------------+-----------------------------+

Not every experiment needs exactly these four panels, but this is the default story of active
foveal perception. The causal narrative it tells:

    scene / current belief
        -> fixation
        -> binocular evidence
        -> epistemic change
        -> persistent 3-D memory
        -> next fixation

## Three visual levels

| level | when | required visuals |
|---|---|---|
| **A** | every executed scientific step | `visuals/<step>/overview.png`, showing the scientific phenomenon, not merely controller bookkeeping |
| **B** | a significant experiment | as appropriate: `overview.png`, key-event visuals, a final reconstruction visual, useful diagnostic plots |
| **C** | a demonstration milestone | as appropriate: `overview.png`, a synchronized frame sequence, MP4, RGB/depth/instance panoramas, object point clouds, a combined scene cloud, a reference/evaluation comparison |

Level-C overhead is not forced onto every bounded experiment.

## Truth semantics in visuals

Where it applies, every visual distinguishes:
- **CONTROLLER-TIME**: what the controller actually had;
- **DERIVED VISUALIZATION**: computed afterwards from controller-time data;
- **REFERENCE / EVALUATION**: Blender truth or evaluation data.

Reference or Blender-truth imagery may appear in a post-run visual only when it is visibly
identified. It never feeds back into controller behavior.

## Reproducibility

Generated visuals stay out of Git; their generators stay in Git. Where it applies, a committed
report states:
- the visual paths;
- the generating tool and the exact regeneration command;
- the source run;
- whether reference/evaluation truth was used.
