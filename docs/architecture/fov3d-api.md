# The `fov3d` API boundary

`fov3d` is the stable conceptual API for all future work in this repository.
`tools/*` is the sealed compatibility engine that implements it today. It is the
Classroom-Oracle-1 golden runtime: byte-identical to legacy `48a3139`, tagged
`baseline-classroom-oracle1-2026-09-25`, and sealed at `consolidation2-sealed-2026-09-25`.

Four rules:

1. **New code imports `fov3d.*`.** Future partition, segmentation and topology code
   imports only `fov3d.*`. It never imports a historical module name
   (`fsg6f_frontier`, `multiobject2c_policy`, …) or `tools.*` directly. The historical
   names describe where code came from, not what it does.
2. **`tools/*` is not edited.** Its files are protected by
   `scripts/verify_baseline.sh` (baseline files unchanged) and by the golden signature
   (`scripts/compare_golden.sh`).
3. **Moving the implementation is optional and not a prerequisite.** The new
   architecture does not need the sealed implementation to move first. If a block is
   moved behind the facade later, it moves one conceptual block at a time. The facade
   name stays, and the move must reproduce the golden signature (full and smoke) with
   0 mismatches. Any change to the protected files is a deliberate, recorded decision,
   because it changes what `verify_baseline.sh` protects.
4. **This step added no behavior.** Consolidation 3 added the facade, the package
   entry points and the durable comparator. It implemented no partition, dual graph,
   segmentation or object discovery.

## Running through the package

From the repository root, with the repo venv:

```bash
.venv/bin/python -m fov3d.experiments.classroom_oracle.run --repo . --out previews/RUN --profile full --device OPTIX
.venv/bin/python -m fov3d.experiments.classroom_oracle.eval --run previews/RUN
scripts/compare_golden.sh previews/RUN                  # 0 mismatches = golden behavior

.venv/bin/python -m fov3d.experiments.classroom_oracle.run --repo . --out previews/SMOKE --profile small --device OPTIX --smoke
scripts/compare_golden.sh --smoke previews/SMOKE
```

From elsewhere, put the repository root on `PYTHONPATH`. The package entry points call the
sealed `main()` and nothing else: argument parsing, defaults, the Blender subprocess
(`blender -b <scene> -P tools/classroom_oracle1_render.py`) and all controller logic are
the sealed code's. The historical entry points (`tools/classroom_oracle1_run.py`,
`scripts/run_golden.sh`) keep working unchanged.

## Package plumbing (`fov3d/__init__.py`)

Importing `fov3d` does two things.

- **It puts `tools/` at the front of `sys.path`.** Every sealed entry point already does
  this, because the sealed modules import their siblings by bare name. Five of them
  (`fsg_stereo`, `fsg6f_frontier`, `multiobject2c_policy`, `classroom_oracle1_matcher`,
  `classroom_oracle1_epistemic`) cannot be imported alone without it.
- **It checks where `tools` resolves.** It raises `ImportError` unless `tools` resolves
  to this repository's `tools/`. A foreign `tools` package ahead on the path is refused,
  not silently re-exported.

## Known properties of the facade (by design; not defects of the engine)

- **Two module objects per sealed file.** A facade module re-exports the `tools.<name>`
  import of a sealed file. The sealed engine itself imports the same file by its bare
  name (`fsg6f_public`, `bl_common`, …). A process that uses both therefore holds two
  module objects with identical code and constants. For example, inside Blender,
  `render_foveated.add_profile` is bare `bl_common.add_profile`, not
  `fov3d.rendering.blender.add_profile`; the facade checker's Blender negative shows this.
  Consequences:
  - treat facade modules as read-only (monkeypatching them does not reach the engine);
  - do not mix class instances between a facade module and the engine's internals
    (`isinstance` across the two copies is false);
  - in one Blender session, render through one route only, because
    `render_foveated._LAST_SAMPLING` is per module object.
- **The public surface is broad.** No sealed module defines `__all__`. The facade therefore
  re-exports every non-underscore name, including the sealed module's own imports
  (`np`, `json`, `cv2`, …). New code should use the documented functions and constants.
  Narrowing the public surface is a later step.
- **Different interpreters.** `fov3d.rendering.blender` and `fov3d.rendering.foveated`
  cannot be imported in the host venv, because the sealed modules import `bpy` at module
  level. `fov3d.stereo.core` and the Classroom `matcher`, `epistemic` and `run` modules
  cannot be imported in Blender, because they need `cv2`. This is the same
  two-interpreter split as the sealed engine.

## Golden signature

`tests/golden/classroom-oracle1-signature.json` (full) and
`tests/golden/classroom-oracle1-smoke-signature.json` (smoke) were generated by
`tools/compare_golden.py signature` from the accepted Consolidation-1 runs. Both the
Consolidation-2 and the legacy frozen runs reproduce them with 0 mismatches.

The signature records the following exactly:

- seeds, the instance catalog, the dense evaluation samples, and the manifest fields;
- per object and per look: counts, gazes and action sources;
- the matcher, fusion, FSG6f and Cyclopean decisions, and the calibration (as canonical-JSON sha256 with readable summaries);
- the map, patch, final-map and observation arrays (as `dtype[shape]:sha256` over canonical bytes);
- the evaluation.

RGB content (`rgb`, `rgb_L`, `rgb_R`) keeps only its dtype and shape. The OptiX Combined
pass is not bit-reproducible, and the controller never reads it.
